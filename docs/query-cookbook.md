# Query cookbook (which source owns which question)

A cookbook of real project-memory questions and how to answer each **correctly**. It pairs
Graphify (fast navigation) with the source you must actually verify against.

> **Read this first.** Graphify returns **leads, not final truth**. It is good at finding the
> relevant file/node quickly; it does not decide whether a record is valid, which fields are
> required, whether the audit passes, or what the roadmap is. After Graphify points you at a
> file or node, **open the real doc / code / CLI output and confirm before you claim anything.**
> For truth and policy questions, the deterministic source *is* the answer and Graphify is at most
> a way to reach it — never the decider.

**Legend**

- **Route — memory:** Graphify genuinely helps; use it, then verify the cited file.
- **Route — truth / policy:** the deterministic source owns the answer; Graphify is at most
  navigation, never the decider.
- **Expect:** *node leads* = nodes with `src=<file> loc=L<line>` pointers; *doc* = read a specific
  document; *CLI* = run a deterministic command and read its output.

Operational how-to (build/refresh/interpret) is in [`graphify-workflow.md`](graphify-workflow.md);
reviewer narrative is in [`query-demo.md`](query-demo.md); concept→file map is in
[`project-memory-map.md`](project-memory-map.md).

## Navigation questions (Graphify helps most)

### What does the synthetic demo prove?
- **Route:** memory.
- **Recommended:** `graphify query "what does the synthetic demo prove?"` for leads, then read the doc.
- **Expect:** node leads into the demo neighborhood (fixtures, `review.py`, schema blocks), **not**
  a finished answer.
- **Verify against:** [`demo.md`](demo.md) (commands + expected output), `scripts/run_synthetic_demo.py`,
  [`sample-record-walkthrough.md`](sample-record-walkthrough.md).
- **Caveat:** observed here, `query` starts from adjacent nodes rather than landing on `demo.md` —
  the actual proof (a schema-valid, audit-clean record regenerated byte-for-byte from synthetic
  fixtures) is stated in `demo.md`, not in a graph node.

### Where is the evidence sidecar explained?
- **Route:** memory.
- **Recommended:** `graphify query "Where is the evidence sidecar explained?"` → read the prose doc.
- **Expect:** node leads to the **implementation** (`export.py`, `build_sidecar()`, `models.py`),
  not the explanation.
- **Verify against:** [`architecture.md`](architecture.md) "Why the sidecar exists",
  [`sample-record-walkthrough.md`](sample-record-walkthrough.md), `src/isaac_records/export.py`
  (`build_sidecar`).
- **Caveat:** the prose lives in the docs; the graph surfaces the code that builds it. Open both.

### Which files implement export?
- **Route:** memory.
- **Recommended:** `graphify explain "export.py"` (node card) and `graphify affected "export.py"`
  (reverse deps).
- **Expect:** node leads — `export.py` calling `validate_official()` + `validate_draft()`, and
  `cli.py` / `audit.py` / `test_export.py` depending on it.
- **Verify against:** `src/isaac_records/export.py`, `src/isaac_records/cli.py`, [`cli.md`](cli.md).
- **Caveat:** `explain`/`affected` need the exact node label; confirm the wiring in source.

### Which files implement validation?
- **Route:** memory.
- **Recommended:** `graphify explain "official.py"` and `graphify explain "draft_validator.py"`
  (or `graphify query "validation"`).
- **Expect:** node leads to **two distinct** validators.
- **Verify against:** `src/isaac_records/official.py` (official schema, gates export),
  `src/isaac_records/draft_validator.py` (no-guessing, gates authoring), [`cli.md`](cli.md).
- **Caveat:** two different validators — don't conflate them; `portal_warnings.py` is advisory, not
  validation (see below).

### Which files implement evidence audit?
- **Route:** memory.
- **Recommended:** `graphify explain "audit.py"` or `graphify affected "audit.py"`; run the CLI for
  behavior.
- **Expect:** node leads to `audit.py`; `isaac audit` output for the real result.
- **Verify against:** `src/isaac_records/audit.py`, [`cli.md`](cli.md); `.venv/bin/isaac audit`.
- **Caveat:** the graph tells you *where* audit lives; only `isaac audit` tells you whether records
  actually pass.

### Where is the CLI documented?
- **Route:** memory.
- **Recommended:** read the doc; `graphify explain "cli.py"` to reach the code.
- **Expect:** a doc + the implementing module.
- **Verify against:** [`cli.md`](cli.md), `src/isaac_records/cli.py`.
- **Caveat:** none significant; the doc is the reference, `cli.py` is the source.

### How do I trace a field from record to evidence?
- **Route:** memory → deterministic artifact.
- **Recommended:** `graphify query "evidence sidecar"` to reach `build_sidecar()`, then read the
  sidecar directly.
- **Expect:** node leads to `export.py`/`build_sidecar()`; the actual provenance is in the sidecar file.
- **Verify against:** `docs/samples/01JQZ0SYNTHXANESDEMO000000.evidence.json` (keyed by official
  JSON-path, plus `assets:` / `descriptors:` / `implicit:` namespaces),
  [`sample-record-walkthrough.md`](sample-record-walkthrough.md), `src/isaac_records/export.py`;
  `.venv/bin/isaac audit` confirms every sidecar key resolves.
- **Caveat:** the graph won't give you a field's evidence value — open the `.evidence.json` sidecar
  for the record and match the JSON-path key.

## Truth / policy questions (the deterministic source is the answer)

### What does the assistant refuse to guess?
- **Route:** truth / policy.
- **Recommended:** read the policy + validator; `graphify explain "draft_validator.py"` only to
  reach the code.
- **Expect:** doc — the no-guessing rules, not a graph verdict.
- **Verify against:** `CLAUDE.md` §5 (no-guessing rules), `src/isaac_records/draft_validator.py`,
  [`sample-record-walkthrough.md`](sample-record-walkthrough.md) "What was refused / blocked"
  (the five `pending[]` blockers: asset sha256s, the reduced spectrum, at least one descriptor).
- **Caveat:** the policy is owned by `CLAUDE.md` + the validator, not the graph.

### What is the difference between validation, audit, and warnings?
- **Route:** truth / policy.
- **Recommended:** read the docs and run each command; Graphify only to reach the modules.
- **Expect:** doc + CLI — three distinct behaviors.
- **Verify against:** [`cli.md`](cli.md), [`portal-warnings.md`](portal-warnings.md);
  `isaac validate <record> --official` (hard gate), `isaac audit` (schema + sidecar coverage),
  `isaac validate <record> --official --warnings` (non-gating advisory).
- **Caveat:** the distinction (hard gate vs. coverage report vs. non-gating advisory) is a policy
  statement — read the docs; don't infer it from graph edges.

### What is deterministic vs. Claude-assisted?
- **Route:** truth / policy (architecture).
- **Recommended:** read the layer map; `graphify query "deterministic core"` only for navigation.
- **Expect:** doc — the four-layer split.
- **Verify against:** [`project-memory-map.md`](project-memory-map.md) "The four layers",
  [`architecture.md`](architecture.md); the Claude layer is `.claude/skills/isaac-*`; the boundary
  is enforced by `test_core_never_imports_graphify` in `tests/test_export.py`.
- **Caveat:** the deterministic-vs-assistant boundary is enforced by a **test**, not by the graph;
  the Claude skills never invent values or override the CLI.

### Why does Graphify not validate records?
- **Route:** truth / policy (design invariant).
- **Recommended:** read the plane separation; this is a design decision, not a query.
- **Expect:** doc — the two-planes rule.
- **Verify against:** `CLAUDE.md` §2 and §7, [`project-memory-map.md`](project-memory-map.md),
  [`query-demo.md`](query-demo.md); the invariant is enforced by `test_core_never_imports_graphify`
  in `tests/test_export.py`.
- **Caveat:** Graphify is a lossy, point-in-time LLM extraction; only the deterministic core and the
  official schema decide validity. Keeping Graphify out of the truth path is deliberate, so a wrong
  or absent graph costs no trust.

### What needs mentor approval?
- **Route:** truth / policy.
- **Recommended:** read the decision register; do **not** ask the graph.
- **Expect:** doc — the open decisions D1–D8.
- **Verify against:** [`mentor-decisions.md`](mentor-decisions.md), [`mentor-brief.md`](mentor-brief.md)
  (e.g. D1 sidecar convention, D2 portal-parity, D3/D4 real-data + LLM-on-real-data, D5 Graphify in
  the demo, D6 next domain).
- **Caveat:** decisions change; the doc **plus the latest human decision** are authoritative — never
  a stale graph snapshot.

### What would need to change for real data?
- **Route:** truth / policy.
- **Recommended:** read the governance + intake + extraction docs.
- **Expect:** doc — the required approvals and the (designed, not built) extraction path.
- **Verify against:** [`data-governance.md`](data-governance.md), [`intake.md`](intake.md),
  [`extraction.md`](extraction.md).
- **Caveat:** real-data support is **not built**. Real or sanitized data requires **explicit written
  data-governance approval** naming the artifacts and the boundary; LLM inspection of real artifacts
  is not allowed by default. Do not imply real-data support exists.

### What is on the back burner?
- **Route:** truth / policy (roadmap).
- **Recommended:** read the roadmap table; do **not** ask the graph.
- **Expect:** doc — the current back-burner list.
- **Verify against:** [`project-memory-map.md`](project-memory-map.md) "Roadmap / back-burner items",
  [`mentor-decisions.md`](mentor-decisions.md) (D6 domain), [`../README.md`](../README.md) status:
  second domain (electrochemistry / performance) — back burner; Web UI — back burner; CI / GitHub
  Actions — later separate phase; license — pending; real/sanitized-data pilot — needs written
  approval; full upstream portal-validator parity — not implemented (evaluation-only seam).
- **Caveat:** roadmap changes; the latest human decision is authoritative, not stale graph memory.
  There is **no web app and no MCP server** in this repo, and portal parity / real-data support are
  **not built** — do not claim otherwise.
