## 1. The six findings that determine the plan's shape

Everything in the sequencing below follows from these. Each was measured this session.

### F1 — Pillar 2 is blocked on DATA, not engineering
This repository contains **no historical BL15-2 source material at all**: zero `.mac`, zero
`.xlsx`/`.xls`, anywhere in the tree. Everything beamline-shaped under `examples/` is generated by
`scripts/make_synthetic_examples.py` with fictional people and a fictional year-2099 session, and is
labelled `SYNTHETIC` in its own header. `openpyxl` is not even a dependency. **The first Pillar 2
deliverable is a data request, not a parser.** §5 forbids designing a parser against assumptions.

### F2 — Pillar 1's endpoint does not exist, and ISAAC *chose* that
`GET /krish/api/mcp` → **404**. The cause is resolved exactly: the body `{"detail":"Not Found"}` is
**ISAAC's own hand-written string** at `apps/api/isaac_api/spa.py:46-47`, where the SPA catch-all
refuses unknown `api/*` paths. **This excludes the Authentik-routing hypothesis** — the request
reached the application and ISAAC declined it. The gate is `app.py:313` → `ISAAC_MCP_DEPLOYMENT`
must be non-empty; it is **unset by default** and `Dockerfile:64-67` does not set it.

**Mounted-vs-unmounted is decidable by status code**, which is the operator preflight:

| Response to `GET .../api/mcp` | Meaning |
|---|---|
| **404** | **unmounted** ← what we observe |
| 405 | mounted, wrong method |
| 403 | mounted, `local-loopback` mode, remote peer |
| 401 | mounted, OAuth on, no token |

One sub-case is already excluded: an incomplete OAuth configuration makes the container **refuse to
boot**, and health answered `200`. What cannot be distinguished from outside: *unset* vs *set to a
fail-closed value*. That ambiguity is itself a gap — **MCP is the only seam that says nothing about
itself on the wire.**

### F3 — Even with every external gate open, no spoken word could enter ISAAC
**There is no MCP note-creation operation**, and `isaac_propose_field_value` **requires** a
`note_id` naming an existing note (the tool's own text says so, `tools.py:1654-1657`). The
proposal channel *is* the product for scientific claims — and it cannot be entered from MCP.
This is the largest app-side gap in the programme and **nobody had filed it.**

Compounding it: only **5 run field paths** (temperature, environment, atmosphere, 2 timestamps) and
**2 record enums** can be asserted over MCP at all. **Pressure has no path.** Composition, sample
identity, instrument and facility are proposal-only. **Free-text observation is impossible.**

### F4 — The ambiguity requirement is one line of code away, and the machinery already exists
Reproduced: `read_transcript("The temperature was around 425 K, maybe 430 K.")` →
**one candidate, 425, `review_required: []`. 430 silently lost.** The *two-sentence* variant
produces **two candidates plus a `conflicting_values_for_one_field` grouping**. The boundary is the
**sentence, not the field**, and the cause is a single line:
`rule.pattern.search(segment.text)` (`transcript_capture.py:810`) returns only the first match.

Three things already exist: `AMBIGUITY_POLICY` already declares this exact case with
`outcome: needs_review`; the grouping is already computed; and `candidate_for_segment` already
anticipates one segment producing two, its comment noting that *"recording one of two proposals
would state a preference this reader does not hold."*

**So the minimal change is `search` → `finditer`**, which lights up correct machinery that is
already there. The real work is at the proposal layer, and it is three narrow things: the grouping
is **computed but never persisted** (`review_required` appears **once** in `routes.py` and **zero**
times in `notes.py`/`proposals.py`); sibling proposals carry **no group link**; and `open` conflates
"unreviewed" with "deliberately undecided" while `conflict_resolution` already has `deferred`.

### F5 — The multi-source historical disagreement model ALREADY EXISTS and is export-correct
For a value already in the draft, README-425 / spreadsheet-430 / `.mac`-430 is representable
**today, with no model change.** The carrier is the evidence envelope:
`evidence_classify.asserted_values` reads each entry's `answer` and returns `conflicting_evidence`
at ≥2 distinct values; `conflict_resolution` stores `competing_values` plus a set-digest, has
`deferred` as first-class, detects staleness on a third answer, and the chosen value
**deliberately never becomes the field's value**. And `build_sidecar` copies the **whole** evidence
list, so the official record carries one value while the sidecar preserves the disagreement.

**Consequence for the plan:** Pillar 2's hardest-looking requirement is mostly already built. Do
not design a new conflict system.

### F6 — Folders need no table, no migration, and no new authorization sentence
`grep -ral folder` → **0 files**; no folder concept exists. But `title` is an exact precedent: an
assistant-side, mutable, organizational string that reaches **neither** the official record **nor**
`content_signature`. Recommendation: a top-level `folder` key in the experiment state document,
included in `_authoritative_signature`, citing the 2026-08-07 lift's *"normal application state"* —
exactly as `ingestion-proposal-contract.md` §8.1 records for proposals.

A `folders` **table** was rejected for a measured reason: it needs `0006` **plus an `ALTER`, which
is a forbidden verb in the write policy** — so it would require weakening the safety policy itself,
and would queue behind an unapproved `0005`. That is a feature that does not work until two humans
act.

**The one mechanical trap that governs every state-document change:** `save_versioned()` returns
`False` **writing nothing** when `_authoritative_signature` is unchanged, and `from_state` drops
unknown keys. So a new top-level key must be a real dataclass field **and** must join that
signature, or the write is silently discarded.

## 2. What this means for sequencing

The two pillars are blocked on **different people**, which is the plan's central scheduling fact:

| Pillar | Blocked on | Can app work proceed? |
|---|---|---|
| **1 — New Science** | Dean (env var, allowlist, Authentik AS), the Claude org Owner (unknown identity), Krish (plan/voice/mobile observation) | **Yes — every app-side item proceeds while all external gates stay shut** |
| **2 — Historical Science** | **Krish + Angel supplying a corpus** | **Only the workflow shell and the review surfaces. No parser.** |
| **Library / UX / Validator / Review** | **nobody** | **Yes — entirely unblocked** |

> **Therefore: do the unblocked work first.** Phases A–C need no external decision at all and
> deliver the largest share of the narrowed product. Phase D is app-side MCP readiness, which also
> needs nothing external. Only Phases E–G wait on other people.
>
> **And the text-chat path depends on voice and mobile availability not at all.** Whatever is
> unknown about Claude Voice, a scientist typing to Claude in a browser exercises the identical
> MCP contract. That is what should be built and demonstrated first — it converts two unverifiable
> capability questions into one demonstrable workflow.

## 3. Phases

Each phase lists its gate, its non-goals, and the decisions it must not take on its own.

### Phase 0 — Recover truth (DONE, this run)
Repository, CI, release, hosted rollout, route inventory, MCP reality, corpus reality, data model,
verification baseline. Recorded in the scope document's §0 and in the ledger's session header.
**Output:** the five planning artifacts. **Gate:** Krish's approval of this plan.

### Phase A — Design system completion + honesty fixes *(unblocked)*
**Why first:** every later UI slice inherits it, and doing it after the redesign means restyling
twice. This is the mechanical half of the UX plan.

- **A1** Add the four missing token axes to `styles/tokens.css`: font size, font weight, line
  height, spacing. Today: **82 tokens, of which 0 are type or spacing**, against **1,073
  hand-authored `font-size` declarations in 20 values**, **8 weights** (including non-standard
  550/620/650) and **2,407 spacing literals in 32 values**. Colour is already 99.3% tokenized with
  zero phantoms — match that discipline, do not disturb it.
- **A2** Decide and apply a real type scale with perceptible steps, and resolve
  `base.css:21`'s `body { font-size: 13px }`. Give the record screen a **visible** page title.
- **A3** Fix the `sr-only` `<h1>`: it reads `"Review Record"` on all four record workspaces and is
  therefore wrong on three. Per-workspace accessible name.
- **A4** Fix and **pin** the two false shipped strings: `HelpPanel.tsx:7` promises draft extraction
  *"from your files"* while `POST /api/uploads` is an unconditional 403 and no path turns a file
  into a draft; `HelpPanel.tsx:10` attributes the whole verdict to the official schema, stale since
  `ok = schema_ok AND exactness_ok`. Extend the `upload-claim-parity` guard family — an unpinned
  correction is one edit away from returning.
- **A5** Reconcile the **two shipped five-step workflow vocabularies** (server-derived spine vs
  `HelpPanel`'s `Draft · Complete · Export · Validate · Audit`). The server's is authoritative
  because it is derived. Make Help reachable from a record screen — today it is only on the `home`
  TopBar variant.

**Non-goals:** no navigation change, no feature removal, no colour-palette change.
**Constraints:** `src/__tests__/interaction-states.test.ts` (P22C — no green/red hex or pass/fail
token in *any* interaction-state rule; it bans the raw hex too, so `base.css`'s
`filter: brightness()` idiom is the sanctioned route) and the phantom-property ratchet are
**honoured, not edited**. Any contrast change is re-transcribed from **Linux CI** with the darwin
column **measured locally**, never carried forward.
**Acceptance:** every token axis declared and referenced; type-scale step count and sizes asserted
by test; a visible `h1` per record workspace whose accessible name matches the workspace; both
false strings corrected and pinned with polarity tests; full suites green; a11y baseline
re-transcribed rather than reasoned.

### Phase B — The Experiment Library *(unblocked; highest value)*
**Why second:** it is the returning scientist's entire experience, and **DEC-07 must land before
the screen**, because the screen cannot be honest without it.

- **B1 (API first)** Extend `GET /api/experiments`. Today it returns only
  `id · title · scenario · status · created_utc · pending_count · evidenced_field_count ·
  exported · record_id`. **There is no `updated_utc`, so "sort by Last Updated" is not
  implementable**; there is no run count, and no technique/beamline. Add what the Library must show
  — and nothing it must not.
- **B2** Library screen: search, sort, status facets, and a row that distinguishes records. The
  shipped worked example has **five records all titled `XANES Example — CuO (Cu K-edge)`**; that is
  the acceptance case.
- **B3** Folders per **F6**: a top-level `folder` state key in `_authoritative_signature`.
  Ship **create / move / delete**; **defer rename**, because rename is **O(N) non-atomic writes**.
  Two costs to state in the PR, not discover: a move bumps `rev` and invalidates held ETags (as
  `title` already does) but **does not** move `content_signature`.
- **B4** Breadcrumbs, cross-folder search, destination choice on create and on import.
- **B5** Reopen-and-continue: land on a record and immediately understand state and next action.

**Non-goals:** no ownership, no sharing, no ACL — blocked by the absent trusted authentication
boundary, not deferred by preference. Four rules keep it from being a rewrite later:
folder is a **label, not a container**; **never** a permission boundary; **never** derived from a
person; any owner stamp is server-set at an ingestion boundary carrying a `trust_basis`.
**Acceptance:** a test proves a folder move changes **no** scientific metadata, **no** record
identity, **no** run value, **no** validation result, and **does not** move `content_signature`;
five identically-titled records are distinguishable in the list; every count shown is the server's
total, never `array.length`.

### Phase C — Experiment workspaces + unified Review + Validator presentation *(unblocked)*
- **C1** Five workspaces (`Overview / Runs / Capture / Review / Record`, labels per **DEC-05**),
  with the server-derived spine reduced to a compact next-action strip. Resolves three navigation
  taxonomies in one rail, and the **three inert workflow steps printing one identical 34-character
  sentence three times**.
- **C2** `Review` as its own workspace (**DEC-08**), consolidating proposals, ambiguities,
  conflicts, unmapped notes, missing information and export readiness — six things living in four
  places today.
- **C3** Collapse the redundancy: **validation is stated in 9 places, next-action in 6 on one
  screen, pending counts in 5**. `WorkflowProgressBanner`'s `excludeSteps` prop — whose comment
  says it exists *"so the same next action never shows twice"* — is the evidence that the
  duplication is structural, and it should become unnecessary rather than load-bearing.
- **C4** Validator presentation only. `schema_ok` stays visible; exactness findings stay in their
  own list and are **never** reported as official-schema errors; advisory warnings can **never**
  turn a PASS into a FAIL; no CLI transcript is reintroduced, because no CLI is invoked.
- **C5** Assistant to 1–2 mounts, collapsed by default, contextual. **Not a directory delete** —
  six lib modules have non-Assistant consumers and `assistant.css` is shared with `GuidedPrompt`.
  `ASSISTANT_NO_MODEL_CLAIM` is preserved **verbatim in substance** on every surviving mount.
- **C6** Evidence Graph out of primary navigation (**DEC-04**). **Ordering is mandatory:** the
  Evidence List must grow a provenance read-out **first**, because
  `GET /experiments/{id}/provenance` loses its only frontend caller and `derived_from` chains would
  otherwise become invisible — removing provenance to simplify the UI, which §38 forbids. Depth of
  removal is **DEC-11**; there is no backend to remove (zero routes, zero backend tests, zero other
  consumers of its lib or CSS). Old `?view=graph` bookmarks cannot break; `list` is already the
  fallback.
- **C7** Scientist-facing labels with schema paths under disclosure — never removed, because the
  path is how a curator maps a field. Today the product prints `reduced_spectrum`, `qc_status`,
  `required_for_evidence_record`, and `Environment & Context context` as copy.

**Raised, not actioned — and larger than the Evidence Graph: Project Memory.** ~7,800 lines,
**578 test cases (the largest single test mass in the app)**, and one of five top-level navigation
slots — for a graph of **this repository's own source code**, shown to scientists. It is a
developer/authoring tool in prime scientist navigation. It was **not** named in the authorizing
directive, so it is surfaced for Krish rather than triaged here.

### Phase D — Ambiguity model + capture provenance *(unblocked; the scientific core)*
- **D1** `search` → `finditer` at `transcript_capture.py:810`, plus the ambiguity acceptance suite.
  **Acceptance is the exact motivating case:** one sentence, `"around 425, maybe 430"` → **two
  candidates, neither preferred, item explicitly unresolved.** A negative control must prove the old
  behaviour is red.
- **D2** Persist the grouping. It is computed today and **served exactly once** (`routes.py:15273`)
  and never stored.
- **D3** Sibling proposals per **Option B** — N proposals plus a **derived** grouping, not a stored
  id. Extending `proposed_value` instead would break `IMMUTABLE_PROPOSAL_FIELDS`, falsify the
  wire-serialized `PROPOSAL_TARGET_SCOPE = 'one_field_path_value_and_evidence'`, change
  `accept_proposal`'s signature and `ACCEPTED_FROM_VALUES`, and leave the OpenAPI **and** MCP
  contracts wrong. Option B changes **none** of the 24 proposal fields.
- **D4** An explicit `unresolved` read, distinguishing "unreviewed" from "deliberately undecided" —
  `conflict_resolution` already has `deferred` as the precedent.
- **D5** *Offered*, never automatic, supersession of a sibling when one is accepted. Today
  accepting one leaves the other open and silently stale.
- **D6** Capture provenance: source channel, utterance, capture session, source text span,
  originating client, proposal creation time, acceptance/edit history. Today a proposal's `source`
  is inherited from the note and `trust_basis` is always `unattributed`, so **a reviewer cannot
  tell "my Claude" from "the CSV importer."**
- **D7** Unify voice + historical import + assistant output (`PROPOSAL_SOURCES` already enumerates
  all four intake classes). **The one case against unifying is CSV** — inherently cross-record,
  with nowhere to live in a per-experiment document — and an apply route for it is a **committed
  human decision, not residual work**.

**Hard constraint carried into every item:** ambiguity is **assistant-side**. The official schema
**does** support uncertainty, but at exactly one path —
`$.descriptors.outputs[].descriptors[].uncertainty` — which is descriptor-only; `context.temperature_K`
has no such sibling. Encoding "425 maybe 430" as `bounds: [425,430]` would assert a continuous
interval nobody stated: the invented range semantics §5 forbids. The codebase already draws this
line in code — `_refuse_a_confidence` rejects scores at any depth while permitting a scientist's own
measured `uncertainty`. **A single value must be chosen before export.**

### Phase E — MCP application-side readiness *(unblocked app-side; demo blocked externally)*
Ordered so that every item proceeds while **all** external gates stay shut.

- **E1 (was G1) — MCP note creation + route-level idempotency key.** The largest and
  highest-value item in the programme: **without it, not one word of a Claude conversation can
  enter ISAAC** (**F3**). Includes a `client_request_key` so a Claude retry cannot double-write.
- **E2** Proposal-channel provenance (shares D6).
- **E3** Default read bounds — now a **vendor-compatibility** requirement, not just efficiency:
  the documented tool-result ceiling is **~150,000 characters** and ISAAC's unbounded reads exceed
  it by roughly **50×** at 1,000 runs.
- **E4** `/api/health` MCP disclosure. **MCP is the only seam that says nothing about itself on the
  wire**, which is precisely why the hosted 404's cause is unresolvable from outside *by
  construction*.
- **E5** Operator preflight tooling, including proving a token's `aud` matches
  **character-for-character**: RFC 8707 permits audience *mapping*, ISAAC's check is exact, so an
  authorization server that maps the audience yields a **100%-failing deployment that looks correct
  from both ends**.
- **E6** A `note` kind in the change feed — the precise signal; today notes reach the feed only
  because they are hashed into `_authoritative_signature`, so the trigger fires on any
  authoritative record change.
- **E7** Proposal deep link — **no `?proposal=` parameter exists** today.
- **E8** One sentence resolving `create_run`'s retry ambiguity.
- **E9** Fix the documented **destructive silent-failure** shape still present at
  `IngestionProposalsPanel.tsx:786`: a background refresh that fails replaces the list and can
  destroy typed text with **no user action at all**. `UnmappedNotesPanel` has the fixed version;
  this one does not.

**What ISAAC can decide that it currently hasn't:** an **authless remote MCP server is explicitly
permitted by the vendor** (auth type `none`, documented "Supported"). ISAAC *chooses* OAuth. That
makes the OAuth requirement ISAAC's decision rather than a vendor gate — a stronger, cheaper
argument to put to Dean, and free, since ISAAC already built OAuth. **Note this does not close the
identity question:** an OAuth bearer yields a `ServicePrincipal`, so **EXT-01 survives EXT-02**.

### Phase F — Remote connector + live-capture demonstration *(externally blocked)*
Order deliberately: **text chat first, voice second.** Prove identity, authorization, run scope,
experiment scope, source provenance, ambiguity, retries, duplicate prevention, network failure,
reconnect, session expiry, the **absence** of Submit authority, and the **absence** of hidden
scientific mutation.

**Vendor facts that constrain this phase** (verified against official documentation 2026-09-12;
full rows in the blockers document):
- Claude connects **from Anthropic's cloud infrastructure**, so the server **and its authorization
  server** must be reachable from `160.79.104.0/21`. The vendor names allowlisting the AS as a
  common failure.
- **No machine-to-machine**: *"Every connection requires user consent."* This matches ISAAC's
  invariants rather than fighting them.
- Custom connectors: **Owner-only on Team/Enterprise**; "Admin" is **not** documented as
  sufficient. **Self-service on Free/Pro/Max** — so a two-scientist pilot needs no organization
  action to connect.
- **Per-tool admin enforcement exists on Enterprise** — an administrator could ship ISAAC
  read-only.
- **Mobile is absent** from the custom-connector availability sentence (*"Claude, Cowork, and
  Claude Desktop"*).
- **Voice + custom connector: UNKNOWN.** The voice article's tool sentence names only *pre-built*
  connectors; "custom" never appears in it, and "voice" appears in none of twelve
  connector/admin/skills documents. **Reported as unknown, not inferred.** One observation by Krish
  settles it — and settles mobile too.
- **Retry behaviour: UNKNOWN** — no vendor guidance exists at all, which is why **E1**'s
  idempotency key is not optional.

### Phase G — Historical Import *(gated on DEC-13; the shell is not)*
- **G-pre (do now)** Issue the **data request**. This is the gate, and it is the phase's first
  deliverable.
- **G1** Import Session + Source Bundle + manifest + source identity, reusing the existing

- **G2** Deterministic parsers, **first wave only after a real sample exists**: filenames and
  directory structure, spreadsheet cells (needs `openpyxl`, currently not a dependency), CSV,
  explicit key/value text. `.mac` **only** once a representative file exists.
- **G3** Semantic reconstruction — run boundaries, legacy synonyms, cross-file reconciliation —
  flowing into **the same** proposal/ambiguity/conflict pipeline from Phase D, with the evidence
  envelope of **F5** carrying multi-source disagreement.
- **G4** The review surface: recognized · parsed · failed · candidate Experiments · candidate Runs ·
  **which source supports each interpretation** · what was inferred rather than read · where
  sources disagree · what is unresolved. Banned pattern: **Upload → Spinner → Mysterious JSON.**
- **G5** Merge into the ordinary Library.
- **G6** Gold-standard evaluation. The metric that matters most is **fabricated-value rate**, not
  fields-filled. Every metric must name the artifact required to compute it; a metric with no
  such artifact is not a metric.

### Phase H — Images / handwriting
Only after the non-image formats work. Same rules: source identity preserved, OCR/model output is
never truth, proposals reviewable, source image referenced, scientist decides.

### Phase I — Hardening and assurance

narrow widths, real microphone. **None of those three is automatable by this tooling** and the plan

## 5. Model assignment

Per the owner's instruction (`DEC-17`, `DEC-18`): orchestration on Opus 5, orchestrator-only
(plan, decompose, review, verify, integrate, commit — **no production code**). **Five sub-agents
total, not five concurrent. Nested spawning forbidden.** Reviewer agents count against the ceiling.

| Work class | Model | Rationale |
|---|---|---|
| Truth/validation/export core, migrations, concurrency, security, authorization, MCP contracts, ambiguity semantics, data model, cross-cutting restructuring | **Opus** | wrong answers here are scientific or security defects |

## 6. "Edit submitted work" — the verdict, because it changes a proposed feature

For a **draft**, the operations already exist; what is missing is UI. Revision history is invisible
even though `isaac_revision_changes` already stores the diff, and `answer_log` is a migration-free
change source.

For a **submitted revision**, the document **stays fully mutable** — no route consults history.
Revision 2 is *a second submission's snapshot*, not an editable draft; there is no draft-revision
entity and no lineage pointer beyond `revision_no`. The blocker is hard:
`reason text NOT NULL CHECK (reason IN ('submission'))`, and `ALTER` is a forbidden verb in the
write policy.

**Recommendation:** reinterpret the UX-visible operation as **"keep editing, then submit again"** —
which is migration-free and is what the system already does — and defer a true draft-revision entity
until a read surface over history exists at all. **One trap the UI must surface rather than hide:**
a rename does **not** move `content_signature`, so submit → rename → resubmit yields
`409 already_submitted`.

### Pass 4 — Architecture / scientific integrity / security
Challenged the plan's own proposals adversarially. **Three findings, all folded in:**

- **The obvious objection to `MCP-001`, answered:** does letting Claude create a *note* put model
  output in the truth path? **No — and the product already says so in its own copy:** a note is
  *"Stored word for word. It is not a field value and not evidence, and it will not appear in an
  exported record."* Notes are structurally inert to export. That is precisely why note creation is
  the safe entry point and a direct field write would not be.
- **But `MCP-001` needs bounds it did not have.** An untrusted in-cluster caller (EXT-01 is open)
  could flood notes. The task now requires **size and rate bounds plus the `client_request_key`**,
  because "inert to export" is not the same as "harmless to the record".
- **`LIB-003`'s acceptance was one assertion short.** It proved a folder move does not move
  `content_signature`, but never that `folder` cannot *reach an exported record or sidecar*. Added:
  a test asserting `folder` appears in **no** exported record and **no** sidecar — the same
  property `title` already has, and the only reason the design is safe.

### Pass 5 — Implementation / dependency / test ordering
Verified each dependency edge. `UX-001 → UX-002`, `LIB-001 → LIB-002/003`, `EVG-001 → EVG-002`,
`CAP-001 → 002 → 003 → 004/005` all hold, and the two ordering constraints that actually matter
(API before Library screen; provenance read-out before graph removal) are enforced in the PR table.
**One cross-cutting interaction found:**

- **Folders will emit change-feed traffic.** Because `folder` must join `_authoritative_signature`
  to be persisted at all, a folder move changes the authoritative signature — and the change feed
  keys on it. So **every folder move emits an `experiment` event and causes a bundle refetch on
  every open client.** That is a correctness-preserving but measurable cost, it is the same cost a
  rename already pays, and it is a second reason to defer rename (which is O(N) writes and would
  therefore be O(N) events).
